容器与虚拟机

Posted 2026-04-08 Other 9 min read
软件工程 概念 容器 Docker 虚拟机 Namespace Cgroup Kubernetes

容器 vs 虚拟机

一句话本质
容器共享操作系统内核，用 Namespace 隔离视野 + Cgroup 限制资源，比虚拟机轻百倍快千倍，但隔离强度不如虚拟机。

第一幕：问题感知

你的公司做了一个电商系统，拆成了 20 个小服务：用户服务、订单服务、支付服务、推荐服务……

按已学方法，每个服务一台虚拟机。20 个虚拟机。

问题来了。

每台虚拟机都要装一个完整操作系统。Ubuntu 最小安装也要 1-2GB 内存。20 个虚拟机，光操作系统就吃掉 20-40GB 内存——而你的服务代码本身可能每个只需要 50MB。

启动一台虚拟机：开机自检、加载内核、启动系统服务……要 30 秒到 2 分钟。你的推荐服务突然流量暴涨，需要紧急扩容 5 台——等 5 台虚拟机全部启动完毕，高峰已经过去了。

每次发布新版本，开发环境用 Mac，测试环境用 CentOS，生产环境用 Ubuntu——同一份代码，在三个环境表现不一样。"在我机器上能跑"成了最常听到的一句话。

有没有比虚拟机更轻的方式来隔离运行应用？

第二幕：引导式构建

虚拟机的"重"，根子在哪？每台虚拟机里跑一个完整的操作系统内核。20 台虚拟机就是 20 份内核在干同样的活儿。

但这 20 个服务其实都跑在 Linux 上。它们需要的内核功能是一样的。

如果这 20 个服务共享同一个内核，只是各自"看到"不同的文件系统、不同的进程列表、不同的网络配置——是不是就不需要 20 个操作系统了？

这就是 容器（Container）的核心思路：不再模拟一整台电脑，而是在同一个操作系统内核上，隔离出多个"看起来像独立系统"的运行环境。

想一想：虚拟机靠 Hypervisor 骗操作系统"你独占硬件"。容器靠什么机制来骗应用"你独占操作系统"？

靠内核自带的两个机制。

第一个叫 Namespace（命名空间）。Linux 内核可以把系统资源"分身"——每个容器看到自己独立的进程列表、独立的文件系统、独立的网络栈、独立的主机名。容器 A 里的进程 ID 是 1，容器 B 里也有进程 ID 1——它们互相看不见。

就像一栋办公楼，每个公司有自己的门禁、自己的电话分机号。你在公司 A 拨 101，接到的是 A 的人；公司 B 也有 101，接到的是 B 的人。但整栋楼的电力、空调——是共享的。

想一想：如果容器只有 Namespace 隔离，容器 A 能不能把整台机器的 CPU 和内存全部吃光，导致容器 B 饿死？

能。Namespace 只管"看不看得见"，不管"能用多少"。所以还需要第二个机制：Cgroup（Control Group，控制组）。

Cgroup 是内核的资源限额机制：规定"容器 A 最多用 2 核 CPU 和 1GB 内存"，超出就限速或杀掉。就像每个公司有自己的电表，超额就断供。

Namespace + Cgroup = 容器隔离的全部底层——一个管"看不看得见"，一个管"能用多少"。

有了底层机制，还缺一样东西：怎么打包和分发？

Docker 引入了 镜像（Image）的概念——一个只读的打包文件，里面包含应用代码 + 所有依赖的库 + 运行配置。在 Mac 上构建，传到 CentOS 测试、Ubuntu 生产——运行行为完全一样。

镜像用 Dockerfile 描述构建过程：

FROM node:20-slim
WORKDIR /app
COPY package.json .
RUN npm install
COPY . .
CMD ["node", "server.js"]

构建：docker build -t my-app . -> 得到镜像。
运行：docker run my-app -> 从镜像启动容器。

想一想：镜像和容器是什么关系？一个镜像可以启动多个容器吗？

可以。镜像是模板（只读），容器是运行实例（可读写）。就像一个 Class 可以 new 多个 Instance。

20 个容器启动只要几秒，内存占用从 GB 级降到 MB 级。但 20 个容器谁来管？哪个挂了要重启、流量大了要扩容——这就是 Kubernetes（K8s）出现的原因：容器编排平台，管理大量容器的生命周期和调度。

想一想：容器共享内核，如果内核有漏洞，一个容器能不能逃逸影响其他容器？

能。这叫容器逃逸，是容器的根本安全边界。虚拟机有独立内核，隔离更强。

第三幕：完整组装

虚拟机 vs 容器：并排架构

虚拟机模型:                          容器模型:

+--------+ +--------+ +--------+    +--------+ +--------+ +--------+
| App A  | | App B  | | App C  |    | App A  | | App B  | | App C  |
+--------+ +--------+ +--------+    +--------+ +--------+ +--------+
| Libs A | | Libs B | | Libs C |    | Libs A | | Libs B | | Libs C |
+--------+ +--------+ +--------+    +--------+-+--------+-+--------+
| 内核 A | | 内核 B | | 内核 C |    |                              |
+--------+ +--------+ +--------+    |    共享的 Linux 内核           |
+------------------------------+    |  (Namespace + Cgroup)         |
|        Hypervisor            |    +------------------------------+
+------------------------------+    |     Docker 引擎               |
|        物理硬件               |    +------------------------------+
+------------------------------+    |     物理硬件 / 云服务器        |
                                    +------------------------------+

核心差异

维度 虚拟机 容器
隔离机制 Hypervisor + 独立内核 Namespace + Cgroup，共享内核
内存开销 每个 GB 级 每个 MB 级
启动速度 30秒~几分钟 几百毫秒~几秒
隔离强度 强 较弱（共享内核）
适合场景 强隔离/不同OS/长期运行 微服务/快速扩缩容/CI/CD

第四幕：验证与压力测试

反事实：没有容器，只有虚拟机

20 个微服务 = 20 个操作系统 = 40GB+ 内存。扩容 5 台等 2-5 分钟。

容器之后：20 个容器 = 1 个内核 = ~1GB。扩容 5 个 = 5 秒。

边界：容器不如虚拟机的场景

强隔离需求：多租户环境用虚拟机，不用容器——内核漏洞影响所有容器。

不同 OS：Linux 容器只能跑在 Linux 内核上，不能混跑 Windows。

有状态服务：数据库等需稳定持久存储的用虚拟机更成熟。

连接

容器和 pnpm 的 store 是同一个思想：pnpm 让多个项目共享同一份 lodash，容器让多个应用共享同一个内核——"相同的部分只存一份，用隔离代替复制"。

现实中的套娃：物理机 -> Hypervisor -> 虚拟机(ECS) -> Docker -> 容器。你在 VPS与云服务器 上跑 Docker 就是这个结构。

容器和 Node.js：Node.js 应用是容器化的最佳候选——轻量、无状态、启动快。Dockerfile 里 FROM node:20-slim 就是在 Node.js 基础镜像上构建。
