CDN（内容分发网络）

一句话本质
CDN 在全球部署边缘节点缓存内容，通过智能 DNS 将用户调度到最近节点，用缓存和回源机制平衡速度与新鲜度。

第一幕：问题感知

你在北京做了一个视频网站，服务器放在北京的机房。

北京的用户打开一个视频，秒开。

乌鲁木齐的用户打开同一个视频，转圈……转圈……5 秒后才开始播放。

你查了一下：北京到乌鲁木齐，直线距离 2500 公里。数据包在光纤里跑一个来回，光是物理传输就要几十毫秒——再加上沿途十几个路由器的排队转发，实际延迟远不止这些。

视频文件很大。一个 5 分钟的视频，可能有 50MB。这 50MB 要从北京的服务器出发，穿越半个中国，到达乌鲁木齐用户的手机。沿途的网络带宽有限，走到某段拥挤的骨干网就堵住了。

更要命的是：如果一万个乌鲁木齐用户同时在看这个视频，这 50MB 要从北京发一万次。同一个文件，走同一条路，重复一万遍。

你加了更多带宽？钱花了不少，乌鲁木齐还是慢——因为距离没变，路由跳数没变，物理延迟是花钱买不掉的。

超市的做法是：总仓库在北京，但全国各地开分店，货提前铺到离顾客最近的地方。

怎么把内容放到离用户最近的地方？

第二幕：引导式构建

超市的分店思路很直接：北京有总仓，乌鲁木齐也放一个仓库，提前把热门商品运过去。顾客来买东西，直接从本地仓库拿，不用从北京发货。

把这个思路搬到网络上：在乌鲁木齐也放一台服务器，提前把视频文件复制过去。乌鲁木齐的用户看视频，直接从本地的那台服务器取，不用跑到北京。

这台放在乌鲁木齐的服务器，就叫做 边缘节点（Edge Node）——它不是你的源服务器，只是一个存放副本的"分店"。

想一想：如果你在全国 30 个城市各放一台这样的服务器，任何用户都能就近获取内容。但问题来了——用户怎么知道应该去哪台服务器取？

用户在浏览器里输入的是你的域名，比如 video.example.com。正常情况下，这个域名会解析到你北京的源服务器 IP。现在全国有 30 个节点，你需要一种机制：根据用户的位置，把域名解析到离他最近的那个节点。

这个机制靠 智能 DNS 调度实现。

普通的 DNS 解析是固定的：无论谁来问 video.example.com 的 IP，都返回同一个地址。智能 DNS 不同——它会看"这次查询是从哪个地区的 DNS 服务器发来的"，然后返回离那个地区最近的边缘节点 IP。

北京用户查询 → 返回北京节点的 IP。
乌鲁木齐用户查询 → 返回乌鲁木齐节点的 IP。

用户完全感知不到这个过程。他输入的还是同一个网址，但背后拿到的 IP 已经被悄悄替换成了离他最近的服务器。

想一想：智能 DNS 根据"查询来自哪个地区的 DNS"来判断用户位置——这个判断一定准吗？如果用户用了一个外地的公共 DNS（比如北京用户用了上海的 DNS 服务器），会发生什么？

会判断错。用户在北京，但 DNS 查询从上海发出，智能 DNS 以为用户在上海，返回上海节点的 IP。用户从北京访问上海的节点，反而比直接访问北京源服务器更远了。

这是智能 DNS 的已知缺陷。现实中有一些补救方案（比如 EDNS Client Subnet 协议，把用户真实 IP 的前缀带上），但不是所有 DNS 服务器都支持。

好，用户被调度到了最近的边缘节点。但这个节点上有他要的内容吗？

视频网站可能有几百万个视频。你不可能把所有视频都提前复制到全国 30 个节点——存储成本会炸。

所以边缘节点不会存所有内容，只存最近被请求过的——这就是 缓存（Cache）。

第一个乌鲁木齐用户请求某个视频时，乌鲁木齐节点上还没有这个文件。节点发现自己没有，就去北京的源服务器取一份，交给用户，同时把这份文件存下来。

第二个乌鲁木齐用户再请求同一个视频，节点已经有了，直接返回，不再去北京取。

这个"第一次没有就去源站取，取完存一份留给后面的人"的动作，叫做 回源（Origin Pull）。

想一想：缓存存了一份副本，但源站的原文件可能会更新。视频的封面图换了，标题改了——缓存里还是旧的。怎么办？

这就涉及到 缓存过期 的问题。

每一份缓存都有一个寿命，叫做 TTL（Time To Live，存活时间）。TTL 到期之后，边缘节点下次收到请求时，不会直接返回缓存，而是先去源站问一下："我手里这份还是最新的吗？"

源站有两种回答。如果内容没变——返回一个"没变，继续用你那份"的轻量响应（状态码 304），节点不用重新下载，直接续期。如果内容变了——返回新内容，节点用新的替换旧的。

想一想：TTL 设多长合适？设太短，节点频繁回源，源站压力大，CDN 的意义被削弱。设太长，用户看到的内容可能过时。你会怎么权衡？

取决于内容类型。视频文件一旦上传很少改——TTL 可以设很长，一天甚至一周。首页 HTML 经常变——TTL 设几分钟。CSS/JS 文件可以用"内容哈希"做文件名（比如 app.3f8a2b.js），内容变了文件名也变，TTL 直接设一年——因为旧文件名的缓存永远不会被请求到。

还有一个场景：你刚发现某个视频有版权问题，需要立刻下架。但全国 30 个节点上都缓存了这个视频，TTL 还没到期。等它自然过期？可能要一天。

这就需要 缓存刷新（Purge）——你主动通知 CDN："立刻删除所有节点上关于这个 URL 的缓存"。CDN 收到指令后，向所有边缘节点广播删除命令，下次用户再请求这个 URL 时，节点发现缓存已被清除，就会回源取最新内容。

想一想：缓存刷新是"全局广播删除"——如果你不小心刷新了整个网站的缓存，会发生什么？

所有节点的所有缓存全部失效，下一波用户请求全部回源。你的源服务器瞬间承受全国所有用户的直接请求——可能直接被打垮。这叫 缓存雪崩。所以缓存刷新要精确到 URL，不要轻易全量刷新。

第三幕：完整组装

CDN 的完整架构

用户（乌鲁木齐）                用户（广州）
      |                              |
      | 1. DNS查询                    | 1. DNS查询
      v                              v
+------------------------------------------+
|           智能 DNS 调度                    |
|  根据查询来源，返回最近的边缘节点 IP         |
+------------------------------------------+
      |                              |
      | 返回乌鲁木齐节点IP              | 返回广州节点IP
      v                              v
+-----------------+          +-----------------+
| 边缘节点（乌鲁木齐）|          | 边缘节点（广州）   |
|  缓存命中? -> 返回 |          |  缓存命中? -> 返回 |
|  缓存未命中?      |          |  缓存未命中?      |
+-----------------+          +-----------------+
      |                              |
      | 回源                          | 回源
      v                              v
+------------------------------------------+
|           源服务器（北京）                  |
|     存放原始内容，是唯一的"真相源"           |
+------------------------------------------+

各组件职责

组件 职责 关键参数
智能 DNS 把用户调度到最近的节点 用户地理位置 / 节点负载
边缘节点 缓存并返回内容 TTL / 缓存容量
回源 缓存未命中时去源站取 回源带宽 / 源站承受能力
缓存刷新 主动清除过期/违规内容 刷新粒度（URL级/目录级）
源服务器 存放原始内容 内容更新频率

端到端示例：乌鲁木齐用户看北京网站上的视频

第一个用户请求（缓存冷启动）：

1. 用户输入 video.example.com/cat.mp4
2. DNS 查询 -> 智能 DNS 检测到查询来自乌鲁木齐
3. 返回乌鲁木齐边缘节点 IP：47.96.x.x
4. 用户连接 47.96.x.x，请求 /cat.mp4
5. 边缘节点检查本地缓存 -> 没有（MISS）
6. 边缘节点回源：向北京源服务器请求 /cat.mp4
7. 源服务器返回 cat.mp4（50MB），携带响应头 Cache-Control: max-age=86400
8. 边缘节点把 cat.mp4 交给用户，同时存入本地缓存（TTL=86400秒=1天）

第二个用户请求（缓存命中）：

1. 另一个乌鲁木齐用户请求 video.example.com/cat.mp4
2. DNS -> 同样返回乌鲁木齐节点 IP
3. 边缘节点检查本地缓存 -> 有，且未过期（HIT）
4. 直接返回缓存的 cat.mp4，不回源
5. 延迟：几毫秒（本地传输），而不是几十毫秒+传输50MB（跨越半个中国）

紧急下架场景：

1. 运营发现 cat.mp4 有版权问题
2. 调用 CDN API：purge("video.example.com/cat.mp4")
3. CDN 向全国 30 个节点广播删除指令
4. 各节点删除 /cat.mp4 的缓存
5. 下一个用户请求 -> MISS -> 回源 -> 源站已删除该文件 -> 返回 404

第四幕：验证与压力测试

反事实：如果没有 CDN，只有源服务器

乌鲁木齐用户每次看视频都要从北京取 50MB。一万个用户同时看 = 源服务器同时发出 500GB 数据。物理延迟无法消除，带宽成本线性增长，用户体验随距离恶化。

CDN 之后：50MB 只从北京传到乌鲁木齐一次（第一个用户触发回源），之后九千九百九十九个用户都从本地节点拿。源服务器几乎无感。

反事实：如果没有缓存过期机制

内容永远不更新。视频封面改了，用户看到的还是旧封面。网站改版了，CSS 缓存还是旧的，页面显示错乱。没有过期机制的 CDN，只适合从不修改的内容。

边界：CDN 擅长什么，不擅长什么

擅长静态内容：图片、视频、CSS、JS、字体文件——这些文件对所有用户都一样，缓存效率极高。

不擅长个性化内容：用户 A 的购物车页面和用户 B 完全不同，无法缓存共享。动态 API 的返回值因请求参数不同而不同——缓存命中率很低。

不擅长实时交互：在线游戏、视频会议——延迟要求在毫秒级，且数据是双向实时流，不存在"缓存复用"的可能。

CDN 不加速"计算"，只加速"搬运"。如果你的网站慢是因为数据库查询花了 3 秒，CDN 帮不了你——它只能让查询结果更快地送到用户手里，但查询本身还是 3 秒。

连接：CDN 与已学知识的关系

CDN 与 SSRF：边缘节点也是服务器，如果节点上跑的服务有 SSRF 漏洞，攻击者可能借边缘节点访问 CDN 内部网络或回源通道。CDN 厂商的节点安全加固，是防御 SSRF 的重要环节。

CDN 与 SDK：云厂商的 CDN 通常通过 SDK 来管理——刷新缓存、查询流量统计、配置 HTTPS 证书，都是调用 CDN SDK 的 API。Client / Signer / Retry 那套机制，在 CDN 管理场景里同样适用。

CDN 与 AKSK：调用 CDN 的管理 API（比如刷新缓存），需要用 AKSK 签名来证明"是你在操作"。如果 AKSK 泄露，攻击者可以刷新你所有缓存（制造缓存雪崩）、修改你的 CDN 配置，甚至把用户流量劫持到恶意服务器。
