Cookie

一句话本质
服务器发给浏览器、浏览器每次请求自动回传的"认人纸条"，补偿 HTTP 的健忘。

第一幕：问题感知

你打开淘宝，登录账号，挑了双鞋放进购物车。然后你点进商品详情页看了会儿评论，再点回购物车——

鞋还在吗？

你觉得这是废话。但对服务器来说，这是个天大的难题。

HTTP 协议（HyperText Transfer Protocol，超文本传输协议）有一个你可能没意识到的性格：它是健忘的。每一次请求都是独立的、一次性的。你点"加入购物车"，服务器收到请求，处理完，回复你，然后——忘了你。下一秒你点"查看购物车"，服务器看到一个请求进来，但它根本不知道这是刚才那个人。

你可能会想：那服务器按 IP 地址记住我不就行了？

问题来了。你家里有 Wi-Fi，全家共用一个公网 IP。你在手机上加购物车，你爸在电脑上也在逛淘宝——服务器只看到一个 IP 发来两种不同的请求。到底是谁的购物车？更糟的是，你从家走到公司，IP 变了，你就不是你了？

那在每个请求里都带上用户名密码呢？先不说每次请求都传密码多危险——你没登录的时候，连用户名都没有，购物车又怎么记住你？

生活中有没有这种情况：两个人之前从没见过面，但第二次见面时，其中一个要立刻认出另一个？

健忘的服务器，怎么认出回头客？

第二幕：引导式构建

留一张"认人凭证"

想象你去一家不认识你的咖啡馆。第一次进去，老板给你一张小纸条，上面写着"3 号客人"。下次你再来，把纸条给他看，他就知道："哦，是 3 号。"

老板不用记住你长什么样，只需要认纸条。

这就是 Cookie（原意"小饼干"，在 Web 里指"服务器交给浏览器保管的一小块数据"）的核心构思。它的工作方式简单到令人怀疑：

第一次访问：
  浏览器 ---- GET /login ----> 服务器
  浏览器 <-- 这是你的纸条 ---- 服务器
                                (Set-Cookie: user=3)

第二次访问：
  浏览器 ---- GET /cart ------> 服务器
           (Cookie: user=3)      "哦，3号来了，给他看他的购物车"

服务器通过 HTTP 响应头里的 Set-Cookie 字段把纸条发下来，浏览器自动存起来。以后每次向这个服务器发请求，浏览器自动在请求头里带上 Cookie 字段，把纸条递回去。

想一想：为什么必须是浏览器"自动"做这件事，而不是让网页的 JavaScript 代码每次手动附带？

（提示：你从淘宝商品页跳到购物车页，中间浏览器重新加载了整个页面。旧页面的 JavaScript 变量全没了。）

纸条上该写什么？

这里有一个关键取舍。

方案 A：纸条上直接写"张三，余额 1024 元，VIP 等级 3"。服务器收到纸条，一看就全知道了，不用查数据库。

方案 B：纸条上只写一串没意义的乱码，比如 abc123xyz。服务器拿着这串乱码去数据库查："哦，abc123xyz 对应的是张三。"

A 快，B 慢（多一次查库）。但 A 有个致命问题：纸条是在用户的浏览器里。用户可以打开浏览器的开发者工具，把"余额 1024"改成"余额 99999999"，再递给服务器。服务器一看纸条，信了。

B 就不会。乱码 abc123xyz 改成 abc123xyy 只会让服务器查库失败——"这是谁？没见过。"

于是实践中演化出了 Session ID（会话标识符）这个概念：Cookie 里只存一个随机生成的 ID，真正的用户数据（登录状态、购物车、权限）保存在服务器的数据库或内存里，ID 是找到这些数据的钥匙。

想一想：如果服务器必须通过查库才能认出你，那每次请求都要查一次库，性能不是很差吗？这个设计在什么场景下会成为瓶颈？

谁来递这张纸条？——"同源"的边界

假设你登录了银行网站 bank.com，银行给了你一张 Cookie 纸条。

几分钟后，你打开一个钓鱼网站 evil.com。这个网站里藏了一段代码，偷偷向 bank.com/transfer?to=hacker&amount=10000 发了个请求。

如果浏览器老老实实把银行的 Cookie 纸条递过去——转账就完成了。你什么都没做。

所以浏览器必须有一条铁律：Cookie 只会递给发它的那个网站。bank.com 发的纸条，只有访问 bank.com 时才会递出去。访问 evil.com 时，银行的纸条绝不出现。

这条规则叫 同源策略（Same-Origin Policy）在 Cookie 上的体现。Cookie 有一个 Domain（域名）属性，决定它归谁所有。

想一想：上面那个钓鱼攻击场景，即使有"只递给同源网站"的规则，其实还是可能成功。为什么？

（提示：evil.com 上的代码发的请求，去向是 bank.com。浏览器判断"该不该带 Cookie"时，看的是请求去向，不是请求来源。）

这个缺口暴露了 Cookie 机制的一个真实漏洞——CSRF（Cross-Site Request Forgery，跨站请求伪造）。为了堵住它，后来又给 Cookie 加了一个 SameSite 属性，告诉浏览器："只有用户当前正在访问我这个网站时，才递这张纸条；从别的网站发起的请求，别递。"

纸条会过期吗？

你登录淘宝一次，半年不退出，淘宝还认你。但你登录网银，十分钟没操作就被踢出去了。

差别在 Cookie 的"寿命"设置。

一种叫 会话 Cookie（Session Cookie）——浏览器一关，纸条就丢。适合银行这种高安全场景。

一种叫 持久 Cookie（Persistent Cookie）——纸条上写着"2026 年 12 月 31 日前有效"，浏览器关了、电脑重启了，纸条还在硬盘里。下次打开浏览器，继续用。

实现方式就是 Set-Cookie 头里带一个 Expires（到期时间）或 Max-Age（存活秒数）属性。没带这俩属性的，就是会话 Cookie。

想一想：淘宝"下次自动登录"是怎么做到的？如果 Cookie 里只存一个随机 Session ID，浏览器关了、服务器内存里的 Session 信息也可能被清了，下次打开怎么还能认识你？

不能让 JavaScript 看到的纸条

Cookie 默认情况下，网页里的 JavaScript 可以通过 document.cookie 读到。方便是方便，但——

如果一个黑客在某个网站的评论区注入了一段恶意脚本（XSS 攻击，Cross-Site Scripting，跨站脚本攻击），这段脚本就能读到你的 Cookie，把你的 Session ID 发到黑客服务器。黑客拿着这个 ID，就能假装是你。

解决办法是给 Cookie 加一个 HttpOnly 属性。加了这个属性的 Cookie，只有浏览器在发 HTTP 请求时会自动带上，JavaScript 读不到。黑客的脚本即使注入成功，也偷不走纸条。

还有一个 Secure 属性——加了它的 Cookie，只在 HTTPS 连接里传输。走明文 HTTP 的时候，浏览器不递。防止中间人窃听。

第三幕：完整组装

现在把第二幕所有零件拼起来，看一个完整的"登录淘宝—加购物车—关闭浏览器—次日重开"的全流程。

全景图

+--------+                                    +--------+
|浏览器  |                                    |服务器  |
+--------+                                    +--------+
    |                                             |
    |  1. POST /login (username, password)        |
    |-------------------------------------------->|
    |                                             |  [验证密码]
    |                                             |  [生成 Session ID: abc123]
    |                                             |  [数据库: abc123 -> 用户张三]
    |  2. 200 OK                                  |
    |     Set-Cookie: SID=abc123;                 |
    |                 Max-Age=2592000;            |
    |                 HttpOnly; Secure;           |
    |                 SameSite=Lax                |
    |<--------------------------------------------|
    |                                             |
    |  [浏览器存纸条到硬盘]                        |
    |                                             |
    |  3. POST /cart/add (item=shoes)             |
    |     Cookie: SID=abc123  <-- 自动带上        |
    |-------------------------------------------->|
    |                                             |  [查库: abc123 -> 张三]
    |                                             |  [张三购物车 += shoes]
    |  4. 200 OK                                  |
    |<--------------------------------------------|
    |                                             |
    |  [用户关闭浏览器]                            |
    |  [纸条仍在硬盘]                              |
    |                                             |
    |  [次日打开浏览器，访问 taobao.com]           |
    |                                             |
    |  5. GET /                                   |
    |     Cookie: SID=abc123  <-- 自动带上        |
    |-------------------------------------------->|
    |                                             |  [查库: abc123 仍有效]
    |  6. 返回已登录的首页                         |
    |<--------------------------------------------|

端到端示例

Step 1. 登录请求

POST /login HTTP/1.1
Host: taobao.com
Content-Type: application/x-www-form-urlencoded

username=zhangsan&password=xxx

Step 2. 服务器响应（发纸条）

HTTP/1.1 200 OK
Set-Cookie: SID=abc123xyz; Max-Age=2592000; Path=/; Domain=taobao.com; HttpOnly; Secure; SameSite=Lax
Content-Type: text/html

<html>登录成功</html>

服务器同时在自己的数据库里记下：

SID         | user_id | expires
abc123xyz   | 1001    | 2026-05-20 14:00:00

Step 3. 浏览器后续请求（递纸条）

POST /cart/add HTTP/1.1
Host: taobao.com
Cookie: SID=abc123xyz

item=shoes&qty=1

Step 4. 服务器识别

收到 SID=abc123xyz
查库 -> user_id=1001 (张三)
操作: 给张三的购物车加 shoes

组装检查

  • Cookie 机制本身（Set-Cookie / Cookie 头）：Step 2, 3
  • Session ID（而非直接存数据）：SID=abc123xyz
  • Domain 限定同源：Domain=taobao.com
  • Max-Age 持久化：Max-Age=2592000（30 天）
  • HttpOnly 防 XSS：HttpOnly
  • Secure 防窃听：Secure
  • SameSite 防 CSRF：SameSite=Lax

每个零件在流程里都有位置。

第四幕：验证与压力测试

反事实

Q1：如果去掉 HttpOnly 会怎样？
网站被 XSS 攻击时，攻击者的 JavaScript 能读到 Session ID，劫持会话。2010 年代大量社交网站账号被盗的根因之一。

Q2：如果去掉 Secure，只用 HTTP 会怎样？
你在咖啡馆连公共 Wi-Fi，任何人用抓包工具都能看到你的 Cookie，拿着它就能冒充你。这就是著名的 Firesheep 插件（2010）引发的恐慌——它让任何人都能在公共 Wi-Fi 下一键劫持别人的 Facebook 会话。

Q3：如果服务器直接在 Cookie 里存 user=zhangsan&is_admin=true 呢？
用户改一个字符：user=zhangsan&is_admin=true → 提权成功。这是初学者最常犯的错，也是为什么必须用不可预测的随机 ID。

边界

什么场景下 Cookie 不够用？

  • 跨域共享登录态：a.com 和 b.com 想共用账号系统，Cookie 的同源限制让它们互相看不到。于是演化出 OAuth、SSO、JWT 等跨域方案。
  • 移动 App：原生 App 没有浏览器那套 Cookie 自动管理机制，通常改用 Authorization: Bearer <token> 这种手动方式。
  • 大小限制：单个 Cookie 通常 ≤ 4KB，每个域下 Cookie 总数也有限制（约 50 个）。复杂的前端状态不能塞进来。
  • 隐私合规：GDPR、CCPA 之后，用于追踪用户行为的 Cookie（比如跨站广告追踪）必须显式征求同意。这就是为什么你现在打开每个网站都要点"接受 Cookie"。

连接

  • 与 JWT（JSON Web Token）的关系：JWT 是另一种无状态认证方案——把用户信息放在 token 里，用密码学签名防篡改。它解决了 Session 方案必须查库的性能问题，代价是无法主动吊销。Cookie 可以装 JWT，两者不是替代关系。
  • 与 localStorage 的关系：localStorage 也能在浏览器存数据，但它不会自动随请求发送，也不受 HttpOnly 保护——不适合存认证凭证。
  • 与 HTTPS 的关系：Cookie 里的 Session ID 在明文 HTTP 下是裸奔的。HTTPS 不是可选项，是前提。
